## 0. 接手者先读

用户的核心目标不是增加更多安全组件，而是让 SkillForge 更好地完成：

1. **生成 Skill**：短对话、明确需求或一次有价值的经历，也应能快速形成初版，而不是等待大量样本。
2. **持续进化 Skill**：任务执行、失败反馈和用户目标变化，都能推动修订；不要只会沿原方向不断补规则。
3. **证明生成与进化有价值**：区分工程机制测试、真实模型对照和生产效果，不用测试数量代替效果证据。

用户明确希望复用旧生成器、显式膨胀检查及 LangGraph 影子编排，避免重造已有模块。

本计划采用的总原则：

> **初版可以早生成、早试用；试用范围与证据强度匹配。广泛复用和正式更新有明确准入条件。**

因此，既不要求“没有三份成功经历就不能生成”，也不把“允许生成”理解为“直接写入正式库并影响所有任务”。

## 1. 用户提出的四个方向：明确决策

| 问题 | 推荐决定 | 实施边界与取舍 |
| --- | --- | --- |
| 初版 Skill 是否放宽？ | **放宽生成和任务内试用。** 短对话或单次经历可形成 Prototype。 | 不放宽工具权限，不伪造成功证据；不会因为样本少就禁止生成，也不会把试用结果直接标成泛化成功。 |
| 旧需求生成器是否保留？ | **保留并复用生成能力，统一候选输出和受控激活。** | 不再维护一条绕过共同晋升条件的正式注册旁路；保留兼容入口，不能直接删除旧功能。 |
| 旧膨胀检查是否复用？ | **优先复用，接到所有修改候选入口。** | 检查“正文增长”不等于判断“技能过载”；比例阈值不能单独决定拆分。 |
| LangGraph 影子编排是否复用？ | **复用为异常候选的有界修复编排器。** | 不接管每次任务、不新建第二套评测器，不让图自动扩权或发布。 |
| 过大 Patch 是否进入图？ | **可进入有限压缩/反思，但先通过便宜的结构、来源与权限检查。** | 不是未经检查直接进图；也不是每个 REVIEW 都自动重试。 |
| 拆分器是否自动启动？ | **首期仅提供受控拆分建议，不自动生效。** | 后续只有确认存在不同适用意图、路由可分且子技能可验证，才考虑正式拆分。 |

核心业务顺序保持：**生成 → 当前任务试用 → 反馈修订 → 验证 → 受控复用**。Runtime、Broker、沙箱、状态机为这条链服务。

## 3. 目标行为：降低生成门槛，不降低使用边界

### 3.1 先采用三个概念阶段，不先发明三套数据库

| 阶段 | 进入条件 | 允许行为 | 不允许行为 |
| --- | --- | --- | --- |
| **Prototype / Draft** | 明确需求、短对话、文档或一次有价值经历。 | 生成、修订、检查；经轻量检查后，在当前授权任务内试用。 | 进入默认全局正式检索；宣称已验证的通用能力；扩大工具权限。 |
| **已试用候选** | 至少有可追溯的试用记录，结果可为 success/failure/unknown。 | 根据新反馈修订；申请适用范围内的验证与晋升。 | 把一次 success 当成泛化证明；把 unknown 伪装成失败或成功。 |
| **正式 Skill** | 对声明范围完成所需验证，并按现有政策获得确认。 | 在批准范围内检索复用、版本化更新和回滚。 | 以未经验证的新内容覆盖已验证版本；超出批准范围无条件复用。 |

“已试用”优先由已有 Candidate + Episode 关系计算，不要求新建中间库或另一套枚举。Prototype 优先复用 DRAFT；确需字段或状态迁移时，先给最小方案。

### 3.2 不再将批量挖掘门槛当成所有生成的门槛

- 显式需求生成：一次明确任务即可创建 Prototype。
- 单次经历生成：允许提炼候选，但标明单次来源及未验证范围。
- 批量模式挖掘：继续使用支持度、结果覆盖度和稳定性筛选，决定是否值得长期整合。
- 正式晋升：根据声明范围和实际评测证据决定，不用“至少三次经历”替代验证，也不机械要求所有场景具备大量样本。
- 原型默认限制在当前任务/会话范围；不要求每次执行都新增人工审批，沿用应用已有授权与副作用审批规则。
- 不为每句聊天都创建 Skill。优先处理用户明确要求保存的流程，或有重复价值的多步任务；相同意图修订已有草稿而非不断新建。

### 3.3 生成器输出统一，但不要再造插件框架

需求生成、Episode 挖掘、文档提取和修补候选最终采用共同的候选数据契约与检查函数。

- 尽可能直接复用现有 Candidate 模型、生成函数和 Store。
- 旧 `generate_skill` 保留文档生成与初始用例建议能力；用薄适配把输出转换为候选。
- 旧 `register=True`/`register_skill` 入口迁移为调用共同注册/晋升路径，保留明确兼容行为和测试；不得继续无提示地绕开正式门禁。
- 无 Episode 的需求或文档使用真实来源类型，不能为满足 `source_episode_ids` 非空而伪造执行经历。
- 优先扩展已有文档/来源引用能力，表达 `requirement/conversation/document/episode` 来源；只保存必要任务摘要、引用和指纹，避免无差别复制整段聊天与敏感环境。
- Skill 正文描述通用步骤和前置条件；订单号、凭据、一次性临时结果不是长期规则。

### 3.4 试用必须真接入执行，不是只生成一个“可试用”标签

当前任务显式选择草稿后，运行时以候选内容快照执行，并记录候选标识、内容指纹、意图版本及结果。

- 复用现有 Runtime/Broker/Collector；不为试用创建一个绕开权限的简易执行器。
- 草稿内容可以通过候选覆盖/上下文注入适配，不必临时写进正式 Registry。
- 新建候选时检查声明工具是否存在、是否在应用授权范围内；需要新增真实工具时报告缺口，不能自动制造权限。
- 执行冻结候选快照，修订草稿只影响后续运行，不改变正在执行的内容。
- 模型返回或工具调用完成不等于业务成功；没有可用验证证据时结果仍为 unknown，但允许保留和继续试用草稿。

## 4. 用户改方向：把“意图变化”纳入演进，而非继续补旧规则

这是本次必须落地的能力，不是以后才考虑的高级 Memory 功能。

### 4.1 最小任务契约

优先在已有任务上下文中表达以下信息，不立刻新建任务管理子系统：

- 当前任务目标与适用业务范围；
- 关键约束和验收条件；
- 意图修订号或等价任务契约指纹；
- 关联的草稿/正式 Skill 及其内容版本；
- 关键假设和来源。

概念名如 `intent_revision`、`task_spec_hash` 是目标语义，不是已存在 API。实际字段由 P0 核准后最小化实现。

### 4.2 变化处理规则

1. 用户明确更改目标、禁止项或交付形式时，更新任务契约并产生新修订。
2. 仅措辞变化、补充不影响流程的信息，不应无意义地生成新意图版本。
3. 模型推测方向变化但缺乏明确依据时，提出确认，不静默重写目标。
4. 当前草稿在旧目标下的结论不自动沿用到新目标；选择 revise 或重新生成，旧草稿标为被替代并保留历史。
5. 同一正式 Skill 在别的场景仍可能有效；单个用户变更目标不能自动全局废弃它。
6. 正在执行的旧版本保持快照。若用户要求停止旧任务，则请求取消；迟到结果只能归属旧意图，不能完成新任务或自动成为新意图的正例。
7. 无法撤销的外部副作用单独报告；版本回滚不能被描述为业务副作用回滚。

意图修订与 Skill 发布版本是两根不同的轴：用户改目标不一定要发布新 Skill，正式 Skill 升版也不一定意味着用户目标改变。

### 4.3 验收样例

- 原任务要求“生成物流处理建议”，用户随后改为“仅核实包裹状态，不提出处理建议”：新草稿移除建议动作，保留查询能力。
- 旧任务结果在变更后返回：不作为新目标的成功结果，不覆盖新草稿。
- 同一任务换一种说法：不新增候选，不重复调用生成器。
- 只读要求变成写入请求：仍受应用权限限制，不因意图变化自动授权写工具。

## 5. 统一准入：复用门禁，按阶段运行，而不是每次都跑最贵的一套

### 5.1 共同检查与阶段差异

| 检查类别 | 生成/当前任务试用 | 已有技能修订 | 正式晋升 |
| --- | --- | --- | --- |
| 来源、用途、Schema、名称与路径 | 必需的轻量检查 | 必需 | 必需且重新绑定 |
| 当前意图和适用范围 | 必需 | 必需 | 必须明确发布范围 |
| 工具契约、应用权限、环境可用性 | 实际使用前检查 | 涉及变更时检查 | 校验声明依赖与实际验证路径 |
| 正文大小/结构化 Diff | 新建检查输出上界；无需多样本门槛 | 与基线比较 | 再确认内容与已验证候选相同 |
| 业务评测 | 当前任务的最低验收；无判据则 unknown | 目标失败与既有正常能力回归 | 使用声明范围内的独立评测依据 |
| 人工确认 | 沿用应用已有执行审批，不额外层层审批 | 普通候选修订不要求每轮确认 | 保留显式晋升条件 |

“统一”指共享定义与判定来源，不是所有阶段都执行完全相同的检查成本。

### 5.2 必须统一的具体边界

- 学习入口采用统一的用途规则；直接调用底层函数不能绕过上层的 learning 限制。
- Episode 来源按 ID 从 Store 读取规范版本，或逐字段核验内容；不能只确认 ID 存在便相信调用方传来的不同正文。
- 需求和文档来源保留其类型；不冒充独立观察或成功证据。
- 门禁输入绑定候选内容、基线（若有）、意图/适用范围、验证配置和数据集版本；仅新增实际需要的字段，不堆一套签名基础设施。
- 涉及工具的候选评测明确区分 fixture、实际 Broker 和真实沙箱，不因类名含 Sandbox 就报告 OS 隔离成功。
- 候选补丁改变依赖或工具调用方式时，复用现有工具校验与必要的 P0 检查；普通文案修改是否需要同等成本由风险策略明确，不隐式跳过。
- 旧注册接口不得绕开共同正式准入；已有调用给明确迁移说明，不静默破坏兼容性。

## 6. Prompt 过载：复用旧防线，并接上有限恢复

### 6.1 分清三个问题

- **长度增长**：可以由字符量、章节比例等确定性指标检测。
- **规则重复/冗余**：需要去重或压缩，长度只是信号。
- **职责冲突/意图混杂**：可能需要拆分，但不能只凭变长就断定。

“请最小修改”属于生成提示，不是强制防线；修复器返回完整文档也不等于一定发生大改，必须比较实际内容。

### 6.2 第一阶段复用既有检查

将现有 `check_prompt_bloat` 接入旧 Patch、新候选修改、RepairJob 和生成器修订路径，保持一个规则来源。

现有默认条件据上轮盘点为：

- 章节增长比例 >25% **并且** 净增 >100 字符；
- 正文超过基线 1.20 倍 **并且** 净增 >100 字符；
- 命中时默认 REVIEW。P0 应再次核对配置和实际比较单位。

不要为了“统一”直接改变原阈值。新建无基线时不能假造空基线套相对增长：使用现有输出预算与绝对正文上界；若没有上界，P0 根据现存 Skill 长度和运行上下文预算提出可解释默认值并记录，不能把任意字符数宣传为行业标准。

### 6.3 过大候选的处理顺序

1. 先做来源、结构、危险动作与工具权限等便宜检查。
2. 再检查 Diff/膨胀，避免先花大量执行评测成本。
3. 对**仅因体积/重复导致审核**、且没有权限/环境/安全阻断的候选，可在启用影子修复策略时进入有限压缩。
4. 压缩保留规则语义、依赖和适用范围；结果作为新候选重新经过共同检查与行为回归。
5. 压缩无进展、持续冲突或预算耗尽，则停止并保留可解释诊断；不得原样发布。

没有启用影子策略时维持 REVIEW，不把一个新恢复流程暗中设成所有用户的默认行为。

### 6.4 拆分不是按长度触发

首期复用拆分器生成建议，默认不执行发布。进入拆分建议前至少确认：

- 有两个可明确说明的任务意图或前置条件，而不是一个必要的长流程；
- 两个子流程的评测目标和路由可以区分；
- 共享工具不被误当成相同意图，也不因共享工具就必须拆分；
- 不存在相互递归依赖或缺少公共步骤；
- 能对原正常任务和新 Badcase 分别验证。

自动创建多技能、改写路由及替换原技能不属于首期必做内容；后续只有真实案例证明压缩无法解决且用户同意扩大范围，才实现这一层。

## 7. LangGraph：复用编排，不重写业务判断

### 7.1 定位

复用既有影子目录、检查点和节点作为**异常候选恢复流程**。普通生成、简单试用和一次验证通过的候选不必经过图。

推荐最小逻辑：读取失败诊断 → 选择一次修订/压缩 → 调用现有生成或修补函数 → 调用统一验证 → 返回候选或停止原因。

这些是逻辑步骤，不要求创建同名新节点或重写现有图。P0 先把实际节点映射到职责，只修改必需连接。

### 7.2 可进入与不可进入的原因

允许有界恢复：

- 可修复的 Skill 行为失败；
- 纯膨胀/重复导致的候选审核；
- 在明确新任务契约下修订当前原型。

不自动恢复：

- 权限或安全拒绝；
- 工具、依赖环境不可用；
- 评测器失效、没有可靠判据；
- 用户取消；
- 指标异常跃升等需要人工判断的 REVIEW；
- 已发布版本与目标基线冲突且尚未重新确认。

不能把“REVIEW”整体解释为“再跑一次图”。用明确 reason code 区分可自动整理与必须审核。

### 7.3 状态与预算

- RepairJob/候选记录保存业务状态；LangGraph checkpoint 保存执行位置，不另建互相竞争的业务真相。
- 图和内部修补函数共享顶层尝试数、Token/调用预算与截止时间，避免“图两轮 × 内部两轮”产生隐藏放大。
- 首期沿用现有有界尝试语义；恢复检查点不能重置次数或重复收费动作。
- 每次修订绑定父候选和基线指纹；基线或意图已变时，旧检查点不能直接继续发布。
- 影子目录只隔离临时文件，不宣称它替代了 OS 沙箱。
- 图成功只返回重新验证过的候选；正式晋升仍走共同入口与确认，不在图节点里另开发布捷径。
- 失败或超时保留简短诊断；不要自动清理用户文件或无限生成新影子目录。

## 8. Trace → 回归用例：补齐反馈，不让评测集自我污染

### 8.1 最小流水线

Episode/评测轨迹 → 筛选可复现业务案例 → 结构化用例提案 → 去重与来源标注 → 确认或确定性批准 → 开发/回归集。

沿用已有 eval trace 和 case 格式。优先实现一个提纯函数与可审查产物，不引入异步多 Agent 或新的向量库。

### 8.2 样本用途

- failure：仅当责任确属 Skill 且有业务预期时，提炼为修补/回归案例。
- success：选取代表性正常案例，防止新修补损坏既有能力；不把每条成功轨迹都转成测试。
- unknown/infra_error：保留诊断，不生成“正确答案已知”的正负例。
- policy/environment：进入权限/执行可靠性专项，不作为改变业务 Skill 的理由。
- evaluation/heldout：不得进入生成或修补输入；一旦用作开发反馈，应重新标注为开发数据，不能继续称最终保留集。

### 8.3 判据与污染控制

- 模型可以协助改写输入和提出断言，但最终预期来自业务规则、可核对工具快照或人工确认。
- 不能以同一模型输出的答案直接作为自己的评分标准。
- 工具快照必须包含足够的输入、输出、状态和契约版本，才能支持重放；敏感字段清理后若影响断言，则转人工而非编造替代数据。
- 按来源任务、派生变体族和意图版本分组拆分数据，不能只按单条文本 hash 划分，避免近重复泄漏。
- 复用旧自动用例比例约束的可用部分；50% 配额不是独立性保证，也不能通过复制人工用例稀释比例。
- 本次补的是可复现的用例提案和受控准入，不默认让每个 Badcase 自动改写最终评测集。

## 9. 模式提炼：先改适用范围，再换复杂算法

优先修正“语义像，但条件不同”的错误合并：

1. 按业务类型/适用范围、意图版本和工具契约兼容性分组，复用现有环境元数据或最少新增字段。
2. 在兼容组内继续使用现有相似度分簇与去重；第一阶段不替换成 DBSCAN，不新增向量数据库。
3. 输出选择原因和弃权原因，并记录实际使用的 embedder/回退方式。
4. 支持度按独立任务统计；同一任务派生的近重复变体不算额外独立业务证据。
5. 正反例都参与适用边界分析，不以“多数成功”掩盖稳定存在的子场景失败。
6. 无法可靠合并时，保留不同范围候选或弃权，不默认向一个 Skill 追加大量例外。

只有业务评测表明现有分簇是瓶颈，才比较更复杂聚类；先比较误合并/漏合并，不以用了 BGE 或 DBSCAN 作为完成标准。

## 10. 商业验证场景与效果实验

### 10.1 场景：电商多包裹物流核查

应用目标：给定订单，查询所有包裹，汇总状态并回答用户。首期全部采用脱敏、可重放的模拟业务数据，不连接真实订单系统。

最小工具契约：查询订单及包裹列表、查询包裹物流。首期只读，不加入退款、赔付、发消息或真实工单创建等副作用。

独立业务判据示例：

- 应查询的包裹全部覆盖，或明确说明缺失状态；
- 所有包裹签收时才允许声称订单全部签收；
- 工具不可用时不能编造物流事实；
- 用户改为“只列状态，不建议后续动作”后，输出不得继续按旧目标生成建议；
- 权限拒绝时正确拒绝也是相应场景的合格行为，不因未调用工具就机械记失败。

### 10.2 三个比较对象

- A：不使用 Skill，使用相同基础任务说明、工具、预算和验证器。
- B：从短需求生成的初版 Prototype/V1。
- C：只利用开发集反馈完成修订后的 V2。

可选消融是“没有意图更新的 V1”与“绑定新意图的修订版”，仅当基础实验能支持时增加，不一开始建立庞大实验矩阵。

### 10.3 数据与实验约束

- 先建立小规模开发集和锁定评测集。建议各 18 个任务，覆盖正常、目标失败、方向变化/边界三类；这是起步规模，不是统计充分性保证。
- 先按任务族分组，再划分开发/评测；使用不同订单/包裹 ID 不能自动视为独立任务族。
- 学习、生成、修补均不得查看锁定评测输入/预期；反复用评测集选版本会使其失去保留集意义。
- 固定模型版本、系统提示、工具契约、预算、缓存策略和评测协议；三组都得到相同的最新用户目标。
- 每任务可重复 3 次观察波动，三组共 162 次评测运行，加上生成/修补成本。执行前先估算费用并由用户批准，不自动调用真实 API。
- 没有真实模型预算时先跑 scripted/fake 集成场景；报告“离线机制验证”，不能报告真实模型收益。

### 10.4 指标与结论

- 主指标：业务契约通过数/总数及逐任务配对变化；分别报告正常能力保持、目标 Badcase 修复、方向变化适配。
- 次指标：错误成功声明、正确拒绝、无进展重试、工具调用数、耗时、实际 Token。
- 基础设施失败单独报告，但不得无说明从分母删掉；同时展示完整样本去向。
- 单独统计生成与进化成本，再说明在多少次复用后可能摊薄；不能只报告执行端 Token。
- Token/费用无采集时填 null/未测，不能用 Fake LLM 固定 usage 当实际成本。
- 先呈现原始案例表和改善/退化对，不保证 V2 必须更好；小样本重复运行不冒充显著性或生产验证。

## 11. 分阶段实施与验收

各阶段产物是最小可演示纵向链路，不是一次性重构整仓。任何阶段发现与当前代码事实不符，先记录偏差，再调整最小接入方式。

### P0：核对入口与冻结验收契约

工作：确认各生成/修补/注册入口、现有候选来源约束、试用接入点、图节点和门禁调用；确定业务任务与检查器契约，并选定新建正文上界。

验收：

- 输出“入口 → 生成输出 → 试用 → 检查 → 晋升”映射，指出所有旁路。
- 核对旧测试定义和兼容需求，不把文档推断当实现事实。
- 记录新字段最小集合及迁移方式；不新建执行器、通用 Policy 平台或另一套 Memory 框架。

### P1：短对话生成与当前任务试用

工作：复用旧生成器生成 Draft，统一来源契约，接入现有 Runtime 的候选快照试用；先打通“生成得早且真的能用”。

验收：

- G1：无历史 Episode，一条明确需求能产生草稿并受控试用，不要求三份支持。
- G2：未晋升草稿不会被另一无关任务的正式检索选中。
- G3：相同请求重复触发不重复注册、不覆盖同名正式 Skill。
- G4：声明未授权工具时，在执行前被拒绝；不能通过草稿试用路径绕过 Broker。
- G5：结果证据不足保留 unknown，草稿仍可修订；不伪造成功 Episode。
- G6：旧 `generate_skill` 默认返回行为保持兼容；显式注册路径不能绕过新的正式准入。

### P2：统一准入与膨胀检查

工作：将共用检查接到生成、显式 Candidate、RepairJob、旧 Patch/注册路径；增加新建上界与已有版本增长检查，先保持 REVIEW，不要求此时实现图恢复。

验收：

- V1：底层显式挖掘拒绝 evaluation/heldout/未知用途；需求来源不必伪造 learning Episode。
- V2：已存在 Episode ID 配上不同内存内容，不能冒充原始证据。
- V3：同一过大修改经不同入口得到相同膨胀诊断；验证临界值、AND 条件和无基线情况。
- V4：候选内容、基线或适用意图在验证后变化，旧记录不能授权晋升。
- V5：带工具候选区分 fixture 与 Broker/沙箱证据，依赖变化不会被当成普通文字修改直接放行。
- V6：普通小改不被迫运行图；轻量试用不要求全套大回归。

### P3：目标变化驱动的草稿修订

工作：接入任务契约修订、草稿替代与旧结果隔离。

验收：

- I1：用户明确改目标后，当前草稿按新目标修订并真实用于下一次运行。
- I2：旧目标的晚到结果不覆盖新目标结果，不作为新意图正例。
- I3：仅改措辞不触发重建，模糊变化不静默替用户作决定。
- I4：用户要求停止时取消旧运行；无法撤销的副作用如实保留，不伪称回滚成功。
- I5：会话目标变化不会全局废弃仍适用于其他任务的正式 Skill。

### P4：轨迹提纯与范围感知挖掘

工作：实现可复现用例提案、来源去重和数据分区；先按范围隔离再复用现有聚类。

验收：

- D1：业务失败可形成带来源、输入和独立预期的用例提案；缺预期则不能自动批准。
- D2：normal 可形成代表性回归用例；unknown/infra 不进入业务成功/失败标签集。
- D3：同一来源和近重复派生不跨入锁定保留集；自动用例比例不能靠复制人工用例规避。
- D4：相似措辞但不同业务范围/工具契约不被错误合并；同一范围多样表达可以归组。
- D5：评测结果可以产生诊断，但锁定评测输入不进入生成/修补 prompt。

### P5：复用 LangGraph 做有界异常恢复

工作：将纯膨胀候选和允许修复的 Skill 失败接入现有影子编排，共用验证与预算。拆分器首期只返回建议。

验收：

- L1：仅因重复/膨胀进入 REVIEW 的候选，可按启用策略压缩，再回共同门禁。
- L2：权限拒绝、环境缺失、评测失效、用户取消不触发模型反复修补。
- L3：外层图与内层 RepairJob 共享预算；恢复 checkpoint 不重置次数、不重复发布。
- L4：重复候选、无进展、超时后停止；结果绑定的意图/基线变化时停止旧恢复。
- L5：图返回 PASS 候选后仍需正式晋升确认，不能在节点里直写正式库。
- L6：长但连贯的单一流程不会被自动拆分；互斥意图可形成建议，但未确认前原技能及路由不变。

### P6：业务对照实验与交接收口

工作：先完成离线纵向验收；获模型预算授权后进行 A/B/C 真实模型实验，整理成功、退化和成本。

验收：

- B1：同一业务案例覆盖需求生成、试用、意图变更、失败修订、验证、确认晋升及未来复用。
- B2：正常任务、目标 Badcase、方向变化和工具故障均有独立业务断言。
- B3：实际结果表区分 scripted/fake、真实模型配模拟工具、真实沙箱，不泛称“全链路真实”。
- B4：呈现 A/B/C 逐任务结果与成本；V2 无提升或有退化也如实报告，不修改锁定评测来制造收益。
- B5：更新现有两份指南和简历事实清单，明确仍未接入或未验证的能力。

## 12. 测试与兼容策略

- 首先围绕新场景增加最小专项测试，再运行被改模块的既有相关专项；不要在每轮小修改后无差别全量跑 tests/。
- 优先复用现有：`test_episode_candidate.py`、`test_mining_and_promotion.py`、`test_pattern_mining.py`、`test_experience_collector.py`、`test_failure_attribution_and_patching.py`、`test_runtime_and_tool_broker.py`、`test_sandbox_execution.py`、`test_retrieval_execution_loop.py`、`test_receipt_and_narrow_repair.py`、`test_end_to_end_evolution_loop.py` 等，实际存在性和覆盖点由执行者确认。
- 旧生成器、Prompt Bloat、LangGraph 和拆分相关测试由 P0 定位，不能猜文件名或直接删除失败断言。
- 数据迁移先保证旧库和未启用快速试用的调用方可继续工作；默认行为变化必须有明确说明。
- checkpoint、候选、版本、source purpose 和调用预算都需做恢复/重复调用专项，避免 happy path 能跑但重启后绕过门禁。
- 测试用例编号 G/V/I/D/L/B 是本计划验收编号，与旧 M1–M5 或历史 F/G/H 编号无关，避免混用旧完成记录。

## 13. 明确不做的事情

- 不把系统重新命名或重建为通用 Coding Agent。
- 不以“贴合 Harness”名义增加多 Agent 集群、任务队列服务、向量数据库或新的 Memory 层。
- 不要求每次短对话生成前都有大量历史样本。
- 不让所有候选必经 LangGraph，不把所有 REVIEW 自动解释为重试。
- 不把过长文档自动拆成多个正式 Skill。
- 不宣称已完全防提示注入、已获密码学来源认证、真实任务绝不退步。
- 不把反思生成的断言直接当成独立正确答案，不以测试数增长代替业务收益。
- 不自动使用真实用户数据、付费 API、外部订单系统或生产发布。

## 14. 每阶段交接记录模板

每完成一个阶段，记录以下内容，控制为摘要而非源码堆积：

1. 本阶段目标与验收编号。
2. 修改文件及职责变化，复用了哪些原模块。
3. 实际入口/调用关系与关键函数位置。
4. 测试命令、退出码、通过/失败/跳过数，mock/real 边界。
5. 未解决场景与本阶段不支持的保证。
6. 新决策与 Trade-off：由谁提出、谁确认，不补造用户参与历史。
7. 下一阶段唯一主要目标；有权限、费用或重要选型阻塞时明确停在何处。

首个可展示成果不是一张更大的架构图，而是：

> 用户给出短需求 → 系统生成可试用原型 → 用户改目标 → 原型随新目标修订 → 执行暴露业务失败 → 定向修补与回归 → 确认后晋升 → 新任务复用正确版本。

## 15. 接手会话的第一条工作指令

> 先阅读此计划，确认它是待实施方案，不把目标行为当作既有事实。核对当前分支与工作区已有改动，保留用户文件。获得实施授权后，从 P0 开始只核对相关入口和已有测试，提交精简接入映射、兼容策略和必要字段方案；随后优先完成 P1 的“短需求生成 + 当前任务受控试用”。不要先重写整个 LangGraph，不要把旧生成器删除，不要为了让测试通过跳过权限、来源或验证绑定。后续按阶段验收，真实模型实验需要单独确认预算。

## 16. 参考与比较边界

- Hermes 官方文档支持从工作流或材料学习 Skill、按需加载及可选写入审批。本计划借鉴“尽早形成可用程序知识”，不照搬其写入策略：[Skills System](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)。
- Hermes Curator 也有整理、归档与回滚，不能将这些功能描述为 SkillForge 独有：[Curator](https://hermes-agent.nousresearch.com/docs/user-guide/features/curator)。
- 用户观察到“改变计划后旧 Skill 没有随之更正”是本计划的需求来源，不据此断言 Hermes 所有版本均没有相关能力。
- 本计划不包含“比 Hermes 更好”的效果结论。先用上述业务场景证明本项目的原型迭代、目标变化适配及受控晋升确实有效。
