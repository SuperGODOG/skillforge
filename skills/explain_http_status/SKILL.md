## Overview
本技能用于解释 HTTP 状态码，尤其覆盖用户遇到的 **4xx 客户端错误** 和 **5xx 服务器错误**。它说明每个状态码在 HTTP 协议中的含义，并给出通用的排查方向；不直接接管代码、日志分析或修改环境。

## Instructions
1. 从用户问题中提取状态码；若给出多位码如 404，按标准原因短语解释；若给范围如 4xx/5xx，先说明类别边界。
2. 按以下模板组织回答：
   - **状态码与含义**：如 `404 Not Found`。
   - **错误类别**：客户端错误还是服务器错误，告诉用户责任边界。
   - **常见原因**：列出该状态码最常见的触发场景。
   - **排查方向**：按“客户端能看什么 → 服务端/网关查什么”的顺序给出可操作建议。
3. 对 IANA/RFC 未登记、但常见于特定网关/服务器（如 Nginx 499、Cloudflare 520）的码，明确标注“非标准/厂商定义”，不要当作通用 HTTP 标准。
4. 如果用户同时问多个状态码，逐个解释并指出共同点/差异。
5. 用户没有提供上下文时，不猜测唯一根因；主动询问请求日志、响应体、出现频率等信息。

## Examples
**Q**：网站突然打不开，Chrome 显示 `502 Bad Gateway`，这是哪里出了问题？
**A**：`502 Bad Gateway` 属于 **5xx 服务器错误**，协议层含义是：网关或代理从上游服务器收到了无效响应。常见原因：反向代理配置错误、上游服务宕机/未启动、超时、DNS 或防火墙阻断。排查方向：先确认网关/代理日志和上游服务健康状态；再检查当前部署、负载均衡及网络策略。若上游是 Java/PHP/Node 等应用，还要查看应用进程和端口是否存活。

**Q**：`429 Too Many Requests` 会自己恢复吗？
**A**：`429` 是 **4xx 客户端错误**，表示用户在一定时间内发送请求太多，服务端做了限流。会否恢复取决于限制策略；通常服务端会在 `Retry-After` 响应头中告诉客户端等待多久。排查方向：查看服务端限流配置，确认是否触发 IP/用户/API Key 维度限制；客户端应退避重试，而不是立刻暴力重试。

## Constraints
- 本技能是纯说明型技能，**不生成代码**，不为用户“改代码/写中间件/做日志采集配置”。
- 不做具体 API 设计决策，例如“这个错误应该返回 400 还是 422”。
- 不虚构标准；未登记或厂商自定义的状态码要如实说明其来源不通用。
- 不承诺解决特定服务器故障；只提供 HTTP 语义和可执行排查思路。若需深入排查，引导用户携带访问日志、响应头和网络环境进行下一步分析。
